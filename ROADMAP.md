# ROADMAP — `@nera-static/plugin-sitemap`

A `sitemap.xml` for every Nera site, built at build time from the final page list, plus a `robots.txt` pointer to it so crawlers find the sitemap without a Search Console entry.

**This file is the single source of truth for the plugin. Extend it; never start a parallel document.** A decision made while working an issue is written back here in the same commit. Each slice below is one plan step; tick it and add a dated `**Done YYYY-MM-DD**` note with anything learned.

Written 2026-10-11 for the Snagio issue `01a1260d-9038-71ac-85ef-772486490e43` ("[nera-plugin-sitemap] sitemap.xml plugin"). `nera-cli/ROADMAP-ai.md` L8 asks for the plugin and points here for the design.

## Where it comes from

`nera-cli/ROADMAP-ai.md` L8 ("Missing plugins") lists `@nera-static/plugin-sitemap` — `sitemap.xml` (+ `robots.txt` pointer) — next to `plugin-feed`. The planned `starter-blog` (L5) needs both. The repository started empty apart from the Snagio issue workflow (`de3f825`).

## The problem

A Nera site ships no `sitemap.xml` and no `robots.txt` unless its author writes them by hand, and a hand-written sitemap drifts the moment a page is added. Search engines still find pages through links, but a sitemap is the documented way to tell them about every page, and both Google and Bing ask for one. A sitemap generated by the build cannot drift.

## The goal

A site adds the plugin, sets `origin` in `config/app.yaml`, and `nera build` writes:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
    <url>
        <loc>https://example.com/blog/hello.html</loc>
        <lastmod>2026-10-01</lastmod>
    </url>
    <url>
        <loc>https://example.com/index.html</loc>
    </url>
</urlset>
```

and, unless the site ships its own, a `public/robots.txt`:

```text
User-agent: *
Allow: /

Sitemap: https://example.com/sitemap.xml
```

No config file is needed; every key has a default (D7).

## Verified facts this design rests on (2026-10-11, core 4.15.1, `../generator/src/`)

- **`getAssets` runs after every plugin's `getAppData`/`getMetaData`.** `setup-plugins.js` step 6 calls each plugin's `getAssets({ app, pagesData })` in plugin order with the final `app` and `pagesData`, so the hook sees pages other plugins generate (e.g. `plugin-tags` overview pages, which carry `layout` and `href`). Core awaits the hook. An entry is `{ from, to }`: `from` absolute (file or directory), `to` relative to `public/`; `validateAsset` rejects an absolute `to` or one that climbs out with `..`. Exists since core **4.13.0**; an older core never calls the hook.
- **Plugin assets are copied theme → plugins → site** (`src/index.js#run`: `copyFolder(theme.assetsRoot)`, `copyPluginAssets`, `copyFolder(assets)`), so a file in the site's assets folder overwrites a plugin's file at the same path, and a plugin's file overwrites a theme package's. `public/` is deleted (`deleteFolder(dist)`) after the plugins ran and before the copies, so anything a hook wrote into `public/` directly is lost.
- **`meta.href` is logical.** `core.js#getPagesData` sets `href` to `/<page path with .md → .html>`, always with a leading slash and `/` separators, never prefixed with `base_path`. `pages/index.md` → `/index.html`, `pages/de/blog/a.md` → `/de/blog/a.html`.
- **`base_path` is applied only to HTML, CSS, `.webmanifest` and `.json`.** `loadAppData` exposes it normalised as `app.basePath` (`''` or `/foo`, no trailing slash). `rewriteHtmlUrls` runs per page; `rewriteAssetUrls` walks `public/` but only touches `.css`, `.webmanifest` and `.json`; `hashAssetUrls` only `.css`, `.html` and `.htm`. A `.xml` or `.txt` file is copied untouched, so **the plugin must apply `app.basePath` itself**.
- **Only pages with `layout` are rendered** (`render.js#createHtmlFiles`: `if (pageData.meta.layout)`). A page without it has no output file, so it must not appear in the sitemap.
- **Frontmatter dates are `Date` objects.** Core parses frontmatter with `yaml` 2.x and `{ schema: 'core', customTags: ['timestamp'], merge: true, uniqueKeys: false }`. Checked: unquoted `date: 2026-01-02` → `Date` (`2026-01-02T00:00:00.000Z`), unquoted `2026-01-02T10:00:00Z` → `Date`, quoted `'2026-01-02'` → string. *(The issue plan first assumed the `core` schema alone, which yields strings; the `timestamp` tag overrides that. D4 was decided on the corrected fact.)*
- **`meta.createdAt` may be the file's birthtime.** `getPagesData` sets `createdAt = frontmatter.createdAt || frontmatter.date || fs.statSync().birthtime`. Both a frontmatter value and the birthtime fallback can be a `Date`, so the plugin cannot tell them apart (D4).
- **The origin.** Core has no `origin` key of its own. `plugin-canonical-links` uses `app.origin` (config/app.yaml), else `app_origin` from `config/canonical-links.yaml`, with trailing slashes trimmed, and builds `${origin}${meta.href}` — up to 2.2.2; since 2.2.3 `${origin}${app.basePath}${meta.href}` (O3, 2026-10-11). `@nera-static/validate`'s output pass (`src/output.js`) resolves the site's own host the same way.
- **Folders.** `app.folders.assets` defaults to `./assets`, becomes `./theme/assets` when a `theme/` folder exists and `folders.assets` is not set (`core.js#computeFolders`). Paths are relative to the site root (the process cwd).
- **The npm name is free.** `npm view @nera-static/plugin-sitemap` returned 404 on 2026-10-11.

## Decisions

### D1 — Generate in `getAssets`, write to `.nera-cache/sitemap/`

The XML is built in `getAssets`, the only hook that sees the final page list (other plugins' generated pages included). It is written to `<site>/.nera-cache/sitemap/<output>` (the cache folder `plugin-images` uses, gitignored by `nera new` since `@nera-static/nera` 1.4.1), and the hook returns `[{ from: <that file>, to: <output> }]` so core copies it into `public/`. Nothing is written into `public/` directly. The hook is synchronous and returns an array in every branch.

On a core older than 4.13.0 `getAssets` is never called and the build would exit 0 without a sitemap, so the plugin fails loudly with the version guard from `plugin-code-blocks` (`src/guard.js`). Because the guard cannot live in a hook that is never called, it runs in `getAppData` (returning `app` unchanged). `peerDependencies` declares `@nera-static/core >=4.13.0` for install time.

### D2 — URLs = origin + basePath + `meta.href`, percent-encoded

`<loc>` is `origin + app.basePath + meta.href`. The origin comes from `app.origin`, else `app_origin` in `config/canonical-links.yaml` (same order as canonical-links and validate), trailing slashes trimmed. `/index.html` is kept as is (not shortened to `/`), so the sitemap names the same URL the site links to. basePath + href are percent-encoded first (amended 2026-10-11, Step 8): `pages/about us.md` → `/about%20us.html`, `über.md` → `/%C3%BCber.html`, characters `encodeURI` does not allow become UTF-8 escapes, a `%` that does not start a valid `%XX` becomes `%25`, and an existing valid escape is left alone, so an already-encoded href is never encoded twice. Lone surrogates become U+FFFD rather than crashing the build. The origin is used as given. Then each `<loc>` is XML-escaped (`&`, `<`, `>`, `'`, `"` — after encoding only `&` and `'` can remain). `exclude` patterns (D3) still match the logical, unencoded `meta.href`.

Without an origin the plugin warns once (naming both places to set it) and produces neither a sitemap nor a `robots.txt`: relative URLs are invalid in a sitemap.

`plugin-canonical-links` builds the same `origin + app.basePath + meta.href` since 2.2.3 (O3, resolved 2026-10-11); up to 2.2.2 it left `base_path` out, so on a `base_path` site its canonical URLs differed from this sitemap's. Percent-encoding (Step 8) is no divergence: canonical-links writes the raw href into an HTML attribute, which browsers and crawlers resolve to the same encoded URL the sitemap names.

### D3 — Which pages

A page is listed when it has a `meta.layout` and a string `meta.href`, unless:

- its frontmatter says `sitemap: false`, or
- its effective `robots` value — frontmatter `robots`, else `app.robots` from `config/app.yaml`, the same `meta.robots || app.robots` the `nera new` layout writes into `<meta name="robots">` — contains `noindex` (case-insensitive, e.g. `robots: noindex, follow`), or
- its `href` matches a config `exclude` pattern: a string compared against the logical `href`, `*` matching any run of characters (including `/`), anchored at both ends — `/drafts/*`, `*/print.html`. Matched with a small hand-written function, no dependency.

Entries other plugins add without `layout` or `href` are skipped, never a crash. URLs are sorted by `href` (plain string comparison) and duplicates dropped, so the same site always gives a byte-identical file.

### D4 — `lastmod` only from authored frontmatter

`lastmod` is the first of `meta.lastmod`, `meta.updatedAt`, `meta.updated` (added 2026-10-15, 1.1.0: the key theme-blog and plugin-feed use), `meta.date` that is a valid date. **`meta.createdAt` is never used**: core may have filled it from the file's birthtime, which CI stamps the same on every file, and the plugin cannot tell an authored `createdAt` from that fallback (decided 2026-10-11, see the verified facts). A site that only sets `createdAt:` gets no `lastmod`; adding `date:` or `lastmod:` fixes that.

Format ([W3C Datetime](https://www.w3.org/TR/NOTE-datetime), as sitemaps.org requires):

- a `Date` at UTC midnight (what YAML makes of `2026-10-01`) → `2026-10-01`;
- any other `Date` → `2026-10-01T09:30:00Z` (ISO without milliseconds);
- a string already in W3C Datetime form (`YYYY`, `YYYY-MM`, `YYYY-MM-DD`, or with `Thh:mm[:ss[.s]]` and `Z`/`±hh:mm`) → verbatim;
- anything else (invalid `Date`, other strings, numbers) → no `<lastmod>`.

No `<changefreq>` and no `<priority>`: both are optional in the protocol and Google ignores them.

### D5 — Multilingual: one sitemap, every language, hreflang alternates

All pages of all languages go into one sitemap, each under its own URL (`/de/…` pages are just pages).

Amended 2026-10-11 (Step 10, closing O1, still in 1.0.0): every listed page that exists in **at least two languages** gets one `<xhtml:link rel="alternate" hreflang="…" href="…"/>` per language, **itself included** (Google requires the self-reference), sorted by `hreflang`, after `<lastmod>`; `<urlset>` then also declares `xmlns:xhtml="http://www.w3.org/1999/xhtml"`. A page with no translation gets none, so a monolingual site's sitemap is byte-identical to one without the feature. A page's language is `meta.lang`, else `lang` from `config/app.yaml` (the same fallback core's `t()` uses).

Pairing translations:

- When `plugin-canonical-links` has filled a non-empty `meta.alternateLinks` on **any** listed page, its pairing is used for the whole site (it honours its `available_languages` and `page_identifier`). Its `href` is `origin + basePath + meta.href` since canonical-links 2.2.3 and `origin + meta.href` before (O3); both forms are resolved back to a listed page by that string (the current form wins if two pages collide) and the URL is rebuilt from that page's `meta.href` like `<loc>` (origin + basePath + percent-encoding).
- Otherwise pages are paired by the frontmatter key `alternates_identifier` (default `slug`, canonical-links' default `page_identifier`): listed pages with a language and the same non-empty value form one group. Within a group the first page per language in `href` order wins. Amended 2026-10-11 (Step 12, still in 1.0.0): when such a group has at least two languages and two or more of its pages share one language, the build warns once per identifier value and language, naming the value, the language and every page (`href` order, the kept one first); the output is unchanged. A group with one language has no alternates, so the duplicate changes nothing and stays silent — a monolingual site never sees the warning. canonical-links' pairing is never checked.

An alternate only ever points at a **listed** page — never at an excluded, `noindex`, `sitemap: false` or layout-less one, and a canonical-links link whose target page has another language than its `hreflang` is dropped. `alternates: false` turns the feature off. No `x-default` entry (no reliable signal for which page is the default).

### D6 — `robots.txt` pointer, on by default

When a sitemap is written and `robots` is not `false`, the plugin also returns a `robots.txt` entry:

```text
User-agent: *
Allow: /

Sitemap: <origin><basePath>/<output>
```

written to `.nera-cache/sitemap/robots.txt`, copied to `public/robots.txt`. If the site ships its own `robots.txt` in its assets folder (`app.folders.assets`, default `./assets`, resolved from the site root), the plugin **does not return the entry** — the site's file is deliberate and is never overridden (the copy order would let the site win anyway; skipping it keeps the intent explicit). A site file the site's `.neraignore` excludes does not count (amended 2026-10-11, Step 12): core never copies it, so the generated pointer is written instead. The match is core's (`render.js` `getIgnoredFiles`/`ignoreFiles`): `.neraignore` read from the site root, one trimmed pattern per line, matched against the path relative to the assets folder with `/` separators — equal, or a prefix followed by `/`; no wildcards. The theme's file is never filtered, because core copies theme assets unfiltered (`index.js`, `copyFolder(theme.assetsRoot, dist, null)`). When that file has no `Sitemap:` line (case-insensitive, at line start), the plugin warns once with the exact line to add.

A theme's `robots.txt` counts the same way (amended 2026-10-11, Step 9, closing O4): core copies theme assets first and plugin assets over them, so a generated file would silently replace the theme's. When the site has no file of its own, the plugin looks for `assets/robots.txt` in the theme root — for `app.theme.package`, the package's `package.json` resolved from the **site** (`createRequire` on the site's `package.json`, as core does), for a local `./…` theme, that path from the site root — and, when it is a regular file, returns no entry. Without a `Sitemap:` line the warning names the theme file and asks for a copy in the site's assets folder with the line added, since a package is not the site's to edit. The site's file still wins over the theme's (only it is checked then). A theme package that cannot be resolved counts as no theme file: core has already failed the build for a `theme:` it cannot resolve.

The `robots.txt` URL is always the site root (`/robots.txt` under `public/`). On a `base_path` deploy crawlers only read `/robots.txt` at the host root, which the site does not control; the generated file is then harmless but unread — the README says so.

### D7 — Config keys (all optional)

Read from the site's `config/sitemap.yaml` via `getConfig` from `@nera-static/plugin-utils`, inside the hook (testable, no module-scope state). A missing file still gives a working sitemap. No views, no templates, no runtime dependency besides `@nera-static/plugin-utils`.

## Configuration — `config/sitemap.yaml`

```yaml
# Where the sitemap lands, relative to public/. Must stay inside public/
# (no leading "/", no "..").
output: sitemap.xml

# Logical hrefs (without base_path) to leave out. "*" matches any characters.
exclude: []
#   - /drafts/*
#   - /404.html

# Generate public/robots.txt pointing at the sitemap, unless the site ships
# its own robots.txt in its assets folder.
robots: true

# hreflang alternates (xhtml:link) for every page that exists in more than one
# language: "auto" writes them when a page has translations, false never.
alternates: auto

# The frontmatter key that pairs translations when
# @nera-static/plugin-canonical-links has not paired them already.
alternates_identifier: slug
```

| key | type | default | invalid value |
|---|---|---|---|
| `output` | string | `sitemap.xml` | not a string, empty, absolute, escaping `public/`, or `robots.txt` (the pointer's path, D6) → warning, default used |
| `exclude` | list of strings | `[]` | a single string is treated as a one-item list; non-strings dropped |
| `robots` | boolean | `true` | anything but `false` counts as `true` |
| `alternates` | `auto` \| `false` | `auto` | `true` counts as `auto`; anything else → warning, default used |
| `alternates_identifier` | string | `slug` | not a non-empty string → warning, default used |

Frontmatter keys the plugin reads: `layout`, `href` (from core), `sitemap`, `robots`, `lastmod`, `updatedAt`, `updated`, `date`, `lang` and the `alternates_identifier` key (`slug`); `meta.alternateLinks` when plugin-canonical-links wrote it; from `config/app.yaml` it reads `origin`, `robots`, `lang` and core's `basePath`/`folders`. It writes no `app.<key>` and no `meta.<key>`.

## XML shape (the public contract)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9"
        xmlns:xhtml="http://www.w3.org/1999/xhtml">   <!-- xmlns:xhtml only when some page has alternates -->
    <url>
        <loc>{percent-encoded, XML-escaped absolute URL}</loc>
        <lastmod>{W3C date}</lastmod>   <!-- only when D4 finds one -->
        <xhtml:link rel="alternate" hreflang="{lang}" href="{URL as for loc}"/>   <!-- D5: per language, ≥ 2 languages -->
    </url>
</urlset>
```

(The real file has `<urlset …>` on one line.)

UTF-8, four-space indentation, `\n` line endings, a trailing newline, `<url>` elements in `href` order. A site with no listable page gets a valid empty `<urlset>`. Changing this shape, the output path, a config key or its default is a contract change (see "Semver notes").

## Semver notes for later changes

Public contract: the config keys and their defaults, the output path, the XML shape above, the `robots.txt` content and when it is generated, and which frontmatter keys include, exclude or date a page. Removing or renaming any of these, or changing a default's meaning, is **major**. A new optional key, a new optional element (e.g. O2's sitemap index) is **minor**. A fix that makes the output match this document is **patch**.

## Not in scope (for now)

- `<changefreq>`, `<priority>` (D4), image/video/news sitemap extensions.
- Pinging search engines (Google retired the ping endpoint in 2023).
- Rules in the generated `robots.txt` beyond `Allow: /` — a site that needs them ships its own file.
